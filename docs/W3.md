## 2 课时 1｜上下文工程与成本

### 2.1 单元 1｜token 成本精算

**为什么先学这个**：Agent 的本质是循环——每轮循环都发一次完整请求（system + 历史 + 工具结果全部重新发送），**成本 = 单价 × 用量 × 轮数**。不会算账，做出来的 Agent 上线即亏损。

**token 计费的基本规则**：

| 规则 | 说明 |
| --- | --- |
| 输入、输出分开计价 | 输入便宜、输出贵（生成更贵） |
| 缓存价 | 命中前缀缓存的输入大幅降价（约 1/10）——详见单元 2 |
| 中文 token | 中文 1 字 ≈ 1—2 token（估算是关键能力） |
| 上下文重复计费 | 每次请求**整个 messages 全部重新计费**，不是只算新增那句 |
| 工具定义也计费 | tools 定义每次随请求发送，按输入 token 算 |

**成本公式（背下来）**：

```
单次请求成本 = 输入tokens × 输入单价 + 输出tokens × 输出单价
Agent 总成本 = 单次请求成本 × 平均循环轮数 × 日调用量
```

**关键洞察：Agent 的成本大头在"输入"**——每次循环把历史全量重发，输入 token 随轮数线性膨胀。10 轮循环 = 第 1 轮的输入被发了 10 次。

**三类任务的成本结构对比**：

| 任务形态 | 输入占比 | 成本特征 | 省钱关键 |
| --- | --- | --- | --- |
| 单次问答 | 低 | 一次调用，成本可控 | 控制输出长度 |
| RAG 问答 | 中 | 每次带检索资料，资料越多越贵 | 精炼资料 + 只带 top-k |
| Agent 循环 | 高 | 输入随轮数翻倍 | 缓存 + 压缩历史 + 减少轮数 |

**成本预算三步法**：

1. 算单次：量级估算（1000 中文字 ≈ 1000—2000 token）× 单价；
2. 乘轮数：Agent 场景乘平均循环轮数（3—10 轮很常见）；
3. 乘规模：× 日活 × 日均次数，得到月度预算线。

**三个省钱手段（优先级从高到低）**：

1. **上下文缓存**：不变前缀（system + 工具定义）命中缓存，输入价大降——Agent 场景收益最大；
2. **压缩输入**：prompt 精炼、检索资料裁剪、历史摘要化（单元 2）；
3. **降档换模型**：flash 档 vs pro 档（W2 单元 3）——简单任务别用贵的。

> 价格以官方定价页为准（https://api-docs.deepseek.com/zh-cn/quick_start/pricing/）；2026-10 另注意 Search/Fetch 接口按次计费（5 元/千次），不是 token 计费。

**面试口径**：“我会在写代码前先算一笔账：单次请求成本 × 循环轮数 × 日活。Agent 的成本大头在输入（历史全量重发），所以优先做前缀缓存和上下文压缩，再谈降档。”

### 2.2 单元 2｜上下文管理策略

**为什么**：窗口大 ≠ 用得好。成本随输入线性涨，注意力随长度衰减（W2 单元 1 的 lost in the middle）。上下文管理 = 在"够用"和"省钱"之间分配预算。

**上下文预算分配（每类各占多少，先规划再写码）**：

```
可用窗口 = 总窗口
        − system 提示词（固定，可缓存）
        − 工具定义（固定，可缓存）
        − 本次检索资料（动态）
        − 历史对话（动态，增长项）
        − 输出预留（max_tokens，保证不截断）
```

**三个核心策略**：

| 策略 | 干什么 | 适用 | 代价 |
| --- | --- | --- | --- |
| 裁剪（truncate） | 丢弃最旧的历史对话 | 对话短、旧消息价值低 | 丢失上文，模型可能"失忆" |
| 摘要压缩（summarize） | 把旧历史压缩成一段摘要，替代原文 | 长对话、长期 Agent | 细节丢失、多花一次摘要调用 |
| 前缀缓存（cache） | 不变的前缀（system+工具）命中缓存，输入降价 | 高频同前缀请求 | 前缀一变（如换 system）缓存即失效 |

**裁剪策略的细节**：LangChain/LangGraph 里常用"保留最后 N 条消息"（trim_messages）或"保留 system + 最近 K 轮"。

**摘要压缩的细节**：不是每轮都摘要——设定阈值（如历史超过窗口 50% 才压缩一次），避免压缩本身成为开销。

**缓存机制的精确理解**：

- 缓存按"前缀"命中：请求的前 N 个 token 与上次一致即命中，命中部分按缓存价计费；
- **前缀一变全部失效**：system 文案改动、工具定义顺序变化都会让缓存作废；
- Agent 场景最大化缓存：把稳定内容（system、工具定义、长期指令）放最前，把动态内容（用户问题、检索结果）放后面。

**lost in the middle 的工程应对（W2 单元 1 的落地）**：

1. 关键信息放开头或结尾（模型对两头记得牢）；
2. 检索资料只带 top-k（相关性排序后截断），不要全塞；
3. 任务指令放最前（system 前置），需要模型"记住"的约束别埋中间。

**面试口径**：“上下文管理 = 预算分配。固定内容（system、工具）走缓存放最前，动态内容（检索、历史）做裁剪和摘要，输出留余量防截断。缓存收益最大，但前缀一变就失效，所以稳定内容要稳定地放前面。”

### 2.3 单元 3｜Embedding 与向量检索原理（RAG 前奏）

**为什么**：工具解决"查数据"，检索解决"读文档找答案"。RAG（检索增强生成）= 先检索相关资料，再注入上下文让模型回答——这是 W4—W5 的正课，本单元先把地基打牢。

**Embedding 是什么（复习 W2 单元 1 ②）**：

- 文本 → 高维向量（几百到几千维），**语义相近的文本，向量距离近**；
- 这是**另一个模型**：Embedding 模型（如 BGE、M3E）与对话模型是两个 API，各自计费；
- 中文场景常用开源 Embedding（BGE 系列、M3E）或厂商 Embedding 接口；本地可跑 sentence-transformers。

**向量检索的核心流程（RAG 的骨架）**：

```
文档 → 切分 chunk → 向量化 → 入库（向量索引）
提问 → 向量化 → 相似度检索 top-k → 注入上下文 → 模型回答
```

**五个关键参数（面试会问）**：

| 参数 | 是什么 | 调优直觉 |
| --- | --- | --- |
| chunk_size（切块大小） | 每段文档切成多少 token | 太小语义割裂，太大检索不精准；200—500 token 起步 |
| overlap（重叠） | 相邻 chunk 重叠多少 | 防止关键句被拦腰切断；50—100 token |
| top_k（召回数） | 检索返回前几条 | 3—5 条常用；越多越贵越杂 |
| 相似度阈值 | 低于阈值的结果丢弃 | 过滤无关噪声；0.7—0.8 起步 |
| 索引类型 | 暴力 / ANN（HNSW 等） | 小库暴力即可，大库用 ANN |

**余弦相似度**：两向量夹角的余弦值，越大越相似（1=同向，0=正交）。检索排序就按它。

**为什么 chunk 切不好 RAG 就废**：模型回答的质量上限 = 检索到的那几段 chunk 的质量。切块是 RAG 里最"手艺活"的部分。

**Embedding 与成本**：Embedding 便宜（单价低）但**量大**（全库都要向量化）；检索时问题向量化每次也要计费。

**面试口径**：“RAG 的地基是 Embedding——语义相近文本向量相近。流程：文档切块 → 向量化入库 → 提问向量化 → top-k 召回 → 注入上下文。质量上限在检索到的 chunk，所以 chunk 切分和召回参数是关键手艺。”

## 3 课时 2｜异步并发与 API 工程化

### 3.1 单元 4｜asyncio 并发基础

**为什么**：Agent 循环里大量时间是**网络等待**（发请求等返回）。串行 = 排队，并发 = 同时等。生产环境要并发，否则延迟和吞吐都不及格。

**核心概念**：

| 概念 | 是什么 |
| --- | --- |
| 协程（coroutine） | `async def` 定义的函数，调用返回协程对象，await 时才执行 |
| 事件循环（event loop） | 调度协程的运行时：谁在等待就让出，谁就绪就运行 |
| await | 挂起当前协程，等异步操作完成——**等待期间不阻塞其他协程** |
| 阻塞（blocking） | 同步 IO 会卡住整个循环，异步里要避免 |

**重要区分：并发 ≠ 并行**：

- **并发**：一个线程里交替执行（IO 等待期间切换）——适合 LLM 这种 IO 密集；
- **并行**：多核同时跑（多线程/多进程）——LLM 调用是网络 IO，并发就够；
- Python 的 GIL 让 CPU 密集任务并行受限，但**异步 IO 不受影响**。

**把 P1 变异步（三步）**：

```python
# 1. 用异步客户端（OpenAI 官方 SDK 的 async 版本）
from openai import AsyncOpenAI
client = AsyncOpenAI(api_key=..., base_url=...)

# 2. 调用时用 await
resp = await client.chat.completions.create(model=..., messages=..., tools=TOOLS)

# 3. LangChain 对应 ainvoke
resp = await llm_with_tools.ainvoke(messages)
```

**并发 + 限流示例（生产级模板）**：

```python
import asyncio
from openai import AsyncOpenAI

client = AsyncOpenAI()

async def ask_one(question: str, sem: asyncio.Semaphore):
    async with sem:                      # 信号量限流：最多 N 个并发
        resp = await client.chat.completions.create(
            model='deepseek-flash',
            messages=[{'role': 'user', 'content': question}],
        )
        return question, resp.choices[0].message.content

async def main(questions: list[str]):
    sem = asyncio.Semaphore(5)           # 同时最多 5 个请求（防限流）
    results = await asyncio.gather(*[ask_one(q, sem) for q in questions])
    return results

asyncio.run(main(['问题1', '问题2', ...]))
```

**为什么必须限流**：并发一开，请求量瞬间放大——API 会限流（429），你的成本也会放大（并发 × 轮数 × 单价）。**信号量（Semaphore）是生产标配**。

**并发与成本**：并发不改变总 token，但改变**速率**——并发越高，单位时间烧钱越快。上线前先算峰值成本。

**面试口径**：“LLM 调用是 IO 密集，异步并发就够了，不需要多线程并行。生产模板：AsyncOpenAI + asyncio.gather + Semaphore 限流——并发提速，信号量防限流，成本按峰值先算账。”

### 3.2 单元 5｜FastAPI 工程化

**为什么**：脚本只能自己跑，服务才能被别人调。FastAPI = 把 P1 变成 `/chat` 接口——可部署、可对接、可并发、可观测。

**FastAPI 最小服务（包 P1 双工具）**：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ChatRequest(BaseModel):
    message: str

class ChatResponse(BaseModel):
    reply: str

@app.post('/chat')
async def chat(req: ChatRequest):
    reply = await chat_loop_async(req.message)   # 单元 6 把 P1 的 chat_loop 改成 async
    return ChatResponse(reply=reply)

@app.get('/health')
async def health():
    return {'status': 'ok'}

# 启动：uvicorn main:app --host 0.0.0.0 --port 8000
```

**流式输出（SSE，生产高频）**：

```python
from fastapi.responses import StreamingResponse

@app.post('/chat/stream')
async def chat_stream(req: ChatRequest):
    async def gen():
        async for token in llm.astream([...]):   # 流式：边生成边出
            yield f'data: {token}\n\n'
    return StreamingResponse(gen(), media_type='text/event-stream')
```

**工程三件套（缺一不可）**：

| 件 | 干什么 | 实现 |
| --- | --- | --- |
| 指数退避重试 | 网络抖动/429 限流时自动重试 | tenacity 库（wait_exponential） |
| 超时控制 | 防止单请求卡死服务 | timeout（如 60s）+ 客户端超时 |
| 限流 | 防自己打爆自己 | Semaphore（单元 4）+ 接口层限流 |

**指数退避示例**：

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=10))
async def call_llm_with_retry(messages):
    return await llm.ainvoke(messages)
```

**生产配置清单**：环境变量（.env / os.getenv）、日志（每请求记录 token/耗时/轮数）、健康检查（/health）、CORS（跨域，给前端调）。

**面试口径**：“脚本要变服务：FastAPI 暴露 /chat，请求响应用 Pydantic 校验；流式用 SSE；工程三件套——指数退避重试（tenacity）、超时、限流。每请求记日志（token、耗时、轮数）是生产排障的地基。”

import asyncio
from tenacity import retry, stop_after_attempt, wait_exponential
from openai import AsyncOpenAI

client = AsyncOpenAI(api_key=..., base_url=...)

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=10))
async def call_llm(messages, tools):
    return await client.chat.completions.create(model=..., messages=messages, tools=tools)

async def run_agent(user_input: str, max_turns: int = 3) -> dict:
    """返回 {reply, turns, input_tokens, output_tokens}"""
    messages = [{'role': 'system', 'content': SYSTEM_PROMPT},
                {'role': 'user', 'content': user_input}]
    for turn in range(max_turns):
        resp = await call_llm(messages, TOOLS)
        msg = resp.choices[0].message
        messages.append(msg.model_dump())
        if not msg.tool_calls:
            return {'reply': msg.content, 'turns': turn + 1,
                    'input_tokens': resp.usage.prompt_tokens,
                    'output_tokens': resp.usage.completion_tokens}
        for tc in msg.tool_calls:
            result = execute_tool(tc.function.name, tc.function.arguments)
            messages.append({'role': 'tool', 'tool_call_id': tc.id,
                             'content': json.dumps(result, ensure_ascii=False)})
    return {'reply': '达到最大轮次，停止', 'turns': max_turns, ...}
